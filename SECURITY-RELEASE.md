# Security release gate

**Current assurance: safe synthetic checks only; actual elevated/cross-user VM validation is UNVERIFIED.** A normal build may produce a development artifact with that status. It cannot be described as security-validated until the gate accepts successful matching VM evidence. This is validation of the documented test matrix, not a security certification or proof of live Hytale compatibility.

## Routine builds

Run unelevated from the repository root on Windows x64 with Git, .NET 10 SDK, Node.js 22 (as used in CI) and Windows PowerShell 5.1:

```powershell
# Prepare this user's package cache; this step needs access to nuget.org.
dotnet restore .\Checks\RuntimeExtraction\RuntimeExtraction.csproj --source https://api.nuget.org/v3/index.json -p:NuGetAudit=false

# Safe checks only; no installer packaging, elevation, live accounts or external services.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File Build-Installer.ps1 -ChecksOnly

# Same checks followed by local installer packaging (does not distribute a release).
powershell.exe -NoProfile -ExecutionPolicy Bypass -File Build-Installer.ps1

# Audit/release-candidate run: also prove that deliberately broken copies fail.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File Build-Installer.ps1 -ChecksOnly -RegressionControls
```

The prerequisite restore downloads runtime packs and single-file build tools for the current self-contained `win-x64` WPF probe. Use the same Windows user, selected SDK and package cache for restore and checks; repeat preparation after an SDK change or when using a fresh cache. The offline build and extraction fixtures use `Checks/VmValidation/NuGet.Config`, which clears package sources. `NU1101` means a required package is unavailable locally: rerun the restore above with package access, require success, then retry the build entry point. Keep those checks fail-closed; do not enable online fallback, bypass checks or elevate to recover.

`Build-Installer.ps1` is the repository's build/release entry point. All its paths run the safe gate first. A direct `dotnet build` is compilation only and supplies no security validation. There is no skip-checks build option. Safe checks refuse an elevated token; never elevate to fix a failure.

When integrating runtime packaging changes, recheck the prerequisite `dotnet restore` command above and both `Build-Installer.ps1 -ChecksOnly` and `Build-Installer.ps1` against the combined source using a fresh disposable package cache. These instructions describe the current probe and packaging, not another branch's implementation.

## Native runtime and elevation startup

The Windows x64 installer is a self-contained .NET/WPF managed bundle with five native WPF sidecars and runtime license notices in the ZIP. Setup and the installed helper load those persistent libraries beside apphost, with no native extraction entries or preinstalled runtime dependency. Windows profile behavior is unchanged.

.NET extracts bundled native files before application startup; setting an extraction variable in `App.OnStartup` or `Setup.RunElevated` cannot protect that boundary. [Microsoft documents the extraction order and directory-permission requirement](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview). The audited host's Temp cache permits additional principals to modify files, so neither ordinary setup nor the everyday helper may extract native code there.

`Setup.ElevationStart` now elevates the absolute system Windows PowerShell executable with an encoded command containing the embedded `Launcher/ElevatedRuntime.ps1` resource and literal quoted arguments. No loose bootstrap script crosses UAC. The existing executable/ancestor pins and new native-sidecar/license pins remain held across the bootstrap and worker lifetime, and the worker retains its existing source, payload, link, ACL and installation checks. This bootstrap is combined with protected module discovery and the read-only shortcut preflight before elevation.

Before starting apphost, the bootstrap checks the Program Files directory and its ancestors for links, trusted ownership and lower-privilege mutation rights. It creates a fresh unpredictable `Program Files\HytaleAccounts-runtime-<guid>` directory with a protected, inheritable DACL granting mutation only to Administrators/SYSTEM, with Administrators ownership. An inheritable OWNER RIGHTS read-control rule suppresses implicit owner WRITE_DAC on extracted children, even if their creator owner is the elevated user's SID. It checks the applied permissions and sets **only the child process's** `DOTNET_BUNDLE_EXTRACT_BASE_DIR`. It never adopts or repairs an existing cache. Unsupported ACLs and mutation allows masked by denies are conservatively rejected. TEMP, TMP, APPDATA, LOCALAPPDATA, USERPROFILE and global directory permissions are unchanged. The worker runs hidden; its exit status returns through the bootstrap. Cache cleanup follows worker exit or startup failure; crashes/locks may leave an administrator-only directory that subsequent runs never reuse. Bootstrap failure returns a setup error without starting the worker.

Use the normal unelevated setup entry point. Directly invoking setup with an elevated token remains unsupported and is rejected in managed startup; the replacement bundle contains no extraction entries even for this invocation. The bootstrap protects the installer-created elevated worker, not arbitrary administrator-created process launches or a compromised same-user installer/controller. Existing trust in Administrators, SYSTEM and TrustedInstaller, and the documented over-the-shoulder source-policy limitation, still apply.

Safe regression coverage is in `Checks/RuntimeExtractionChecks.ps1`. It uses a private disposable fixture and a harmless published single-file WPF probe, substituting the fixture user for Administrators only in a disposable bootstrap copy. Checks cover protected creation, pre-existing cache preservation, individual foreign mutation grants, junction rejection, actual native extraction before application initialization, WPF native module paths, poisoned inherited cache isolation, literal argument forwarding, profile preservation, nonzero status propagation and cleanup after failure. Actual extracted DLLs must inherit OWNER RIGHTS; Windows Authz models an ordinary owner against those DACLs and positively detects the implicit WRITE_DAC regained by removing that ACE. `-Mutation CacheEnvironment` deliberately removes the child environment assignment in a disposable copy and must fail at the native extraction assertion; the release gate runs it with `-RegressionControls`. The same harmless probe also demonstrates the unsafe ordinary route: native files extracted before managed entry inherit a disposable foreign Modify grant. A second publish using the replacement no-extraction settings runs under setup/helper filenames with that pre-existing cache, loads WPF from sidecars, preserves cache bytes, creates no cache on a fresh start, rejects missing sidecars, forwards arguments and retains the normal profile. The OrdinaryExtraction negative control deliberately turns extraction back on in the disposable probe and must fail its module-path assertion. Setup checks reject incomplete/foreign-writable sidecars and verify source pins, staging locks and cleanup. These are unelevated synthetic checks, not real administrator/cross-user enforcement evidence. The combined runtime-sidecars-v2 VM contract requires fresh actual Windows identity observations for the changed package; no such evidence is supplied by these host checks.

After publishing and creating the release ZIP, the build runs `Checks/RuntimePackageChecks.cs` against the **actual release bytes**, without loading or executing setup. It checks the .NET bundle manifest, included Core/WPF runtime configuration and libraries, all seven embedded setup/bootstrap resources against source, and ZIP membership and byte hashes. Results are saved as `dist/RUNTIME-PACKAGE.json`. The self-contained distribution now requires the setup EXE, five native WPF DLL sidecars and both license/notice files together. Native or unknown bundle entries and legacy extraction flags fail inspection; each DLL must match the publish output and ZIP bytes. No preinstalled .NET runtime is required. Installed payloads include the same DLLs/notices with the helper published last; uninstall removes only these exact owned files. This inspection fails closed on an unknown bundle format or compressed entries pending review.

**Still unverified:** actual UAC (both same-user and another administrator), real second-user attempts to write/delete/replace the runtime directory during extraction/loading, production Program Files creation/cleanup with a full token, SYSTEM behavior, interruption/antivirus locks, signing and live installation/accounts. The current host run does not request elevation or perform any of these actions. A release claim requires fresh authorized disposable-VM evidence for this changed startup boundary, including native module paths and runtime directory ownership/DACLs during the elevated worker's lifetime; the extended VM harness defines a mandatory runtime matrix, but no actual run of it has been established.

Integration on **2026-11-01 (Europe/Amsterdam)** preserves all ten contributing branch tips through merge commits. The six older fixes already have evolved implementations on the audited main: empty staging cleanup, installer removal recovery, logout fallback despite storage failures, pending-login shutdown preservation, identity-based renamed shortcut restoration, and cancellation recovery with finalization confirmation. Integration retains these newer checks and behavior rather than restoring the older implementations.

For this combined source, run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Build-Installer.ps1 -RegressionControls`. The gate includes all runtime and module controls. Installer fixtures also run read-only preflight after discovery repair and verify that relocated records, edited shortcuts and original backups remain unchanged. Results for the exact tested Git revision and source fingerprint are written to `dist/security/<run>/report.json`; package inspection is in `dist/RUNTIME-PACKAGE.json`, and `dist/SECURITY-STATUS.json` binds the package hash to that report. Earlier branch-local report paths and artifact hashes do not describe this integration. Without fresh matching real-world evidence, `SecurityValidated` must remain false.

Graphify is queried before source exploration and regenerated from combined source. Its output is locally ignored; no graph files are tracked at this base or added by integration.

The checked-in [GitHub Actions workflow](.github/workflows/checks.yml) runs safe checks and all regression controls for pushes and pull requests, then packages a development installer with its licenses. GitHub's hosted Windows runner starts as administrator, so `Checks/Run-CiChecks.ps1` creates a disposable standard user, loads its profile, restores the single-file runtime probe's prerequisites from nuget.org into that user's package cache, runs the unchanged safe gate with that token, and removes the user afterward. Prerequisite restore must succeed before checks begin; the extraction fixtures still clear package sources, so a missing pack remains a failure rather than an online fallback inside the gate. This bootstrap is allowed only on GitHub-hosted runners and must not be run on a personal machine. It does not run the actual privileged VM matrix or publish releases. CI retains synthetic logs and the development ZIP for 14 days; preserve release evidence separately. Require the `Windows safe checks` status on `main` when GitHub branch protection is available.

The optional negative controls remove the install, uninstall or publisher module-path restrictions, disable finalization confirmation, destination pinning, membership checking, ACL propagation suppression, path pins, mutation policy, private replacement, body timeout, handler timeout, or outstanding-handler slot retention, or introduce a wrong adapter jump destination or pc metadata offset in disposable source copies. Each must exit nonzero at its expected regression; compile errors or surviving mutations fail the gate. Normal builds run the positive suites; mutation builds are an explicit audit cost.

Installation and publisher verification supply the Windows system module directory explicitly. Windows PowerShell may also add its protected Program Files module directory during startup. Uninstall sets `PSModulePath` with .NET system paths immediately after parameter binding, before its first cmdlet: shell elevation cannot supply a custom child environment. `-NoProfile` alone does not prevent automatic module loading; removing `PSModulePath` restores default discovery, including writable user locations.

Run `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File Checks/PowerShellModuleRegressionChecks.ps1` for the focused suite. It compiles a disposable source copy, observes the real publisher `ProcessStartInfo` at `Process.Start`, and maps absent/empty module paths to a fixture directory to model writable default discovery. The real signature command still runs in Windows PowerShell. Controls prove the substitute modules execute and can return a false valid Hypixel signature. The uninstall fixture runs the captured production command without elevation and stops at its first safety dependency, before removal operations. `-Mutation InstallModules`, `-Mutation UninstallModules` and `-Mutation PublisherModules` must each fail their corresponding assertion. These are isolated regression checks; actual elevated discovery and real signed-launcher acceptance remain unverified.

The default C# entry point and `--safe` run the generated adapter fixtures before stopping at the legacy lifecycle/native executable checks. `--native-adapter` runs just those fixtures. Safe checks use fake bytes and loopback listeners; they do not inspect the installed launcher or credential storage. Native binary and live integration checks are separate opt-in work and are not evidence from this gate. See [the audit](SECURITY-REAUDIT.md) for remaining limitations.

## Actual VM evidence and the release claim

Prepare a fresh package and perform the complete [disposable VM runbook](Checks/VmValidation/README.md), including normal UAC, over-the-shoulder UAC, unrelated standard-user attacks, actual administrator/SYSTEM staging, both real repair tasks, failure cleanup and sentinels. Only an explicitly authorized isolated disposable VM may execute those scenarios. Ordinary builds never launch a VM or request UAC. Older packages without source/SDK provenance must be rebuilt, not relabeled.

After guest `Verify` and `Cleanup`, copy the complete `ModLauncherSecurityVM-Evidence-<id>` export to a local evidence directory. Then run:

```powershell
# Check the release claim without creating an installer.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File Build-Installer.ps1 `
    -ChecksOnly -SecurityValidated -VmEvidence C:\ReleaseEvidence\ModLauncherSecurityVM-Evidence-<id>

# Local release-candidate packaging with the same mandatory gate.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File Build-Installer.ps1 `
    -SecurityValidated -VmEvidence C:\ReleaseEvidence\ModLauncherSecurityVM-Evidence-<id>
```

Replace the placeholder with the actual exported directory. `-SecurityValidated` fails before packaging when evidence is missing, incomplete, failed, simulated, hash-mismatched or stale. Without that switch, the safe build can succeed but records `SecurityValidated: false`, `VmStatus.Status: unverified` and the reason. A VM pass alone cannot bypass failing synthetic checks.

The gate requires a successful schema-2 actual-VM summary, matching source fingerprint/SDK, hash-verified fixed evidence manifest, distinct actor identities and UAC token types, denied unrelated-user operations with successful positive controls, restrictive captured staging ACLs, failure/sentinel outcomes, SYSTEM staging, and successful SYSTEM/limited repair/task results. OTS rejection of a different user's source remains an **expected fail-closed compatibility limitation**, not proof that an OTS installation works.

## Provenance, freshness and retention

Every run writes `dist/security/<UTC>-<id>/report.json` and per-step logs, even when a check fails. The report records Git HEAD, dirty status, per-file SHA-256 hashes, aggregate source fingerprint, OS/build, architecture, filesystem, PowerShell, SDK, Node, timestamps, exact command/argument arrays, exit codes, expected negative failures, log hashes, safe status and VM status. A dirty-tree pass applies to those exact bytes, not to HEAD alone. Source changes during checks or packaging fail validation.

The fingerprint includes all non-Markdown, non-ignored files under `Launcher/` and `Checks/`, root PowerShell/C#/solution/build scripts, global/NuGet/Directory.Build configuration and `.github/workflows/`. It includes untracked additions and marks tracked deletions. Changes to storage/ACL helpers, bridge code, elevation/staging, installer/repair scripts, embedded resources, checks, harness, gate or build configuration therefore require **fresh full VM validation** before the claim. An SDK change also invalidates VM evidence. Documentation-only commits can reuse a matching run; both the guest's tested revision and the current revision remain recorded.

Maintainers must also request fresh VM validation for changed target Windows/runtime/security policy, new supported filesystems/architectures, new security findings, or build inputs added outside the fingerprint's coverage. The gate does not infer these changes. Evidence proves only the recorded guest configuration; other configurations remain unverified. Review the fingerprint's file list when adding build inputs.

Local packaging emits `dist/SECURITY-STATUS.json`, binding the installer, full ZIP and sidecar SHA-256 values to the safe report hash and VM status. It also creates `HytaleAccounts-Setup.zip` containing the executable, five native WPF DLL sidecars, MIT `LICENSE` and `THIRD-PARTY-NOTICES.txt` collected from the exact runtime packs used in that publish. Missing runtime license text fails packaging. `SHA256SUMS.txt` covers the ZIP, executable, every native sidecar and both license files. Preserve those files, the whole safe-report directory and the complete VM export together. `dist/` is ignored and is not durable evidence unless retained by the maintainer. Never reuse metadata for a different installer hash. No command here publishes or modifies external services.

Until both actual VM validation and the README's live acceptance sequence have passed, publish only explicitly experimental prereleases. Mark older versions lacking the current security fixes unsupported. Link users to `/releases`, not `/releases/latest`, which can select an older regular release or be unavailable when only prereleases exist. Review logs/status metadata for local paths and identities before attaching public evidence. See [SECURITY.md](SECURITY.md) for publication settings and reporting.

Evidence is unsigned, maintainer-supplied test output, not remote attestation. A compromised builder/guest administrator can forge it. Trust the reviewed source, build environment, VM operator and retained evidence. Simulated Authz access, deterministic races and fabricated evidence-schema tests must always be reported separately from actual user-token/elevation enforcement. No live credentials, real installation/authentication/gameplay, exhaustive races, sustained denial-of-service, or compatibility outside the recorded environment are certified.

## Runtime evidence contract update

Schema 2 and runtime-sidecars-v2 require **ordinary startup, same-user elevation and alternate-administrator elevation** alongside every existing staging/UAC/task requirement. Runtime rows bind run/source, actual process/token identities, worker PID, ready-file hash and UTC lifetime. They require zero pre-application extraction, loaded WPF sidecar paths, all five DLL hashes matching the VM package manifest and protected persistent directory/file ownership/DACLs. Independent unrelated-user mutation attempts and filtered-owner attempts for elevated rows retain equivalent positive controls. Elevated rows also require attacks on the separate empty bootstrap cache. Profile/poison and persistent-library preservation, exit propagation and cache absence after worker exit/start failure are mandatory; persistent libraries are retained until fixture cleanup.

Missing, failed, stale, inconsistent or rehashed-but-invalid runtime records remain unverified. A matching source fingerprint alone never establishes coverage. Guest Verify and the release gate share the same semantic validator; Cleanup exports the same fixed runtime manifest. Synthetic schema acceptance uses fabricated records only in disposable parser tests and never supplies actual VM evidence or release validation.

See the [runtime matrix](Checks/VmValidation/README.md#runtime-bootstrap-matrix-mandatory-schema-2). The collector and gate now match the combined sidecar packaging. Fresh actual VM execution is still required; fabricated schema tests and harmless host probes cannot supply that evidence.

Actual VM execution remains **UNVERIFIED**. The collector observes loaded-worker enforcement after extraction; extraction-time races, interrupted processes/antivirus locks, SYSTEM runtime startup and live installation/accounts remain outside this newly collected runtime matrix. Existing SYSTEM staging and task evidence remains mandatory. Ordinary safe builds keep SecurityValidated false without complete matching actual-VM evidence.
